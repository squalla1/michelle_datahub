## 一、取数口径

### 1.1 typed `content/{module}?by=fetched` 返空 —— 当前不复现

9 个模块逐个实测（08-05 04:10 UTC），8 个返回当日条目：

```bash
for m in calendar macro market events news opinion company channel; do
  printf "%-9s " $m
  curl -s "https://mai.polarisagi.com/api/v1/content/$m?by=fetched&limit=3" \
    | python3 -c "import json,sys;d=json.load(sys.stdin);print(len(d), d[0]['fetched_at'] if d else '')"
done
```
```
calendar  3 2026-08-05T04:06:56    market    3 2026-08-05T04:07:27    news      3 2026-08-05T04:03:44
macro     3 2026-08-05T00:06:15    events    3 2026-08-05T04:05:39    ...
```

### 1.2 跨类型 `/content?module=X&by=fetched` 返旧 —— 口径说明，不是弃用

设计上 `by` **只决定 `date=` 过滤作用在哪个时间字段**，不参与排序。因此带不带 `by`
返回完全一致的结果（实测同样的 id）：

```bash
curl -s ".../api/v1/content?module=market&by=fetched&limit=2"   # [(753037, 04:07), (753036, 04:07)]
curl -s ".../api/v1/content?module=market&limit=2"              # 同上
```

反馈中"published 2014 的旧条"是 **published_at 的语义**：日历项的 published_at = 事件日期。
近两天入库的条目里事件日期最早到 2009 年（锁定期解禁 394 条、BOJ 日程 42 条、FOMC 日程 19 条）——
条目是新抓的，只是它描述的事件很早。

**已处理**：新增 `order=` 参数，需要按发布时间排序时直接指定，两种口径都保留。

```bash
curl ".../api/v1/content?module=news&order=published&limit=20"   # 按发布时间倒序
curl ".../api/v1/content?module=news&limit=20"                   # 默认按入库时间倒序
```
接口文档（中英双版）已补上"`by` 只控过滤、`order` 控排序"以及 published_at 的模块语义说明。

### 1.3 events typed 取不到最新 —— 当前不复现

`content/events?limit=3` 首条 fetched 08-05 04:04 / published 08-05 03:35，与跨类型接口一致。

### 1.4 排序稳定性与响应抖动（核查中新发现的两件事）

**批内顺序不确定 —— 已修。** 同一批写入的条目 `fetched_at` 完全相同，此前没有第二排序键，
返回首条是随机的（这正是五.2 的表象）。现在统一以 `id` 倒序兜底，并加了
`(module, fetched_at)` / `(module, published_at)` 两个复合索引（生产库已建）。

**响应时间整体抖动 —— 需服务器侧处理。** 同一时刻实测：

| 端点 | 多次测量 |
|---|---|
| `/health`（完全不查库） | 1.4s / 2.9s / 6.7s |
| `/api/v1/content/news` | 1.5s / 4.5s / 9.1s |
| `/api/v1/sources?limit=1` | 6.6s / 25.0s / 37.9s |

同一条查询在数据库端 `EXPLAIN ANALYZE` 只要 **0.015 毫秒**，而不查库的 `/health` 也要几秒 ——
瓶颈不在数据库或某个模块，而在服务器 CPU：刷新与正文抽取任务和 API 抢同一台机器。
已把正文抽取并发从 8 降到可配置的 4（`DATAHUB_FULLTEXT_WORKERS`）；
彻底解决需要给服务器扩 CPU，或把调度器挪到另一台机器。
**这也是 8-04 那批"取不到数据"最可能的真实来源**——客户端超时较短时，慢响应就表现为空。

## 四、数据管线

### 4.1 补图 —— 原因查明，已改善

近 2 天、入库超 1 小时的 news 共 22,505 条，15,074 条有图（67%）。拆开看：

| 来源类型 | 条数 | 提取失败 | 有图 |
|---|---|---|---|
| 非 Google News 的 RSS | 14,859 | 1,434（10%） | 12,674（85%） |
| Google News RSS | 7,646 | 4,588（61%） | 2,400（31%） |

**不是补图任务没跑**：Google News 链接早已解码成真实地址（4,247 条失败项 100% 带 `canonical_url`），
失败发生在目标站——抽样 12 条实测 NYT 403、Reuters 401、Axios 403、WSJ 401，全是付费墙/反爬。

**已处理**：正文抽取改用浏览器 UA（订阅抓取仍用原 UA——Reddit 对浏览器 UA 限制更严）。
同一批 URL 的 A/B：WSJ 从 401 变 200 并拿到 og:image。修改后实跑 40 条新闻：
**提取成功 31 条、补图 26 条**（此前 Google News 批次成功率 39%）。
剩余失败仍是 NYT/Reuters 这类硬付费墙，属数据源本身限制。

### 4.2 opinion 断更 —— 三个根因，一个已修复，两个需外部条件

1. **StockTwits(629 / 477)：已修复上线。** 原因是"公开API"这种方式没有对应插件，运行被 `skipped`。
   已实现 StockTwits provider，实跑两源各 30 条入库，带股票代码、情绪、价格：
   ```bash
   curl "https://mai.polarisagi.com/api/v1/content?source_id=629&limit=3"
   ```
   ```json
   {"title": "$SPCX Morningstar maintained its one-star rating…",
    "payload": {"symbol": "SPCX", "sentiment": "Bearish", "price": 115.98, "platform": "StockTwits"}}
   ```
2. **RSSHub 系 52 个源（含微博 589–591）：路由已修，仍需一个自建实例。**
   根因有两层：登记表里这些行有的填站点页地址（`https://s.weibo.com/top/summary`）、
   有的填 `https://RSSHUB_HOST/...` 占位符，而抓取器只认"路径"形式，于是直接请求原站，
   被反爬挡下后还被记成 `ok / 0 条`（所以监控看不出异常）。
   已做三件事：① 站点地址→RSSHub 路由的映射（微博/雪球/知乎/B站/即刻/Threads 等，含 12 条单元测试）；
   ② `RSSHUB_HOST` 占位符自动替换；③ 拿不到 feed 的响应改记 `error` 并写明原因，不再伪装成正常。
   **剩下的外部条件**：公共实例 `rsshub.app` 已被 Cloudflare 全面拦截（实测 6 条路由全部 403，
   另试 4 个公共镜像也都不可用），需要自建一个 RSSHub（一条 docker 命令）并配置
   `DATAHUB_RSSHUB_BASE_URL`。另有 15 个人物源登记的是微博昵称（`weibo.com/leijun`），
   RSSHub 只接受数字 uid，这批会明确标注 `skipped` 并写明原因，需要在登记表补 uid。
3. **Reddit（598–614）：需要出口代理或官方 API 凭据。**
   实测确认是 IP 限流而非偶发：同一 IP 顺序请求 5 个子版，即使间隔 5 秒，也只有第 1 个 200、
   其余全部 429。已加 `DATAHUB_HTTP_PROXY` 配置项（所有抓取与正文抽取统一走该出口，已实测生效），
   服务器侧配置一个可用代理即可恢复；更稳妥的是申请 Reddit 官方 API 凭据。
