## 二、逐条复核

### 1 · 前瞻事件集中于单一批次

**结论**:成立。
**依据**:事件日期晚于当日的共 11,325 条,`fetched_at` 全部落在 2026-08-15;08-17、08-18、08-19 三个批次各 0 条,最远事件日期为 09-12。
**处理**:日历分片窗口逻辑未上线所致,发版后重新验证。核查方"该批次于 08-22 过期后前瞻数据归零"的推断成立。

### 2 · asset_class / benchmark / image_probe 回退

**结论**:成立。
**依据**:08-17 至 08-19 三个批次的 `asset_class` 取值仅有 `二级市场`、`Forex`、`Commodities`、`Crypto`,六个规范中文值零命中;`benchmark` 字段仅在 08-15 批次出现 49 条;`image_probe` 自 08-15 后无新增。另据 `EURUSD` 仅在 08-15、08-18 两个批次出现,常驻基准逻辑确未生效。
**处理**:非版本回滚,系新代码从未部署。发版后重新验证。

### 3 · 管道停摆、清理未恢复

**结论**:成立,现已恢复。
**依据**:复核时 API 全量最早 `fetched_at` 为 2026-08-12 08:00,最新为 2026-08-19 16:06,跨度 7 天,清理任务运行正常。
**处理**:核查方关于"清理与抓取属两个独立任务"的判断正确。08-15 至 08-17 的停摆原因无法从 API 侧判定,需调取服务器日志,另行排查。

### 4 · event_from / event_to 未生效

**结论**:成立。
**依据**:两个参数未出现在 `openapi.json` 中,FastAPI 对未声明参数静默忽略,因此六种参数写法与不传参数返回结果完全一致;返回条目的 `event_date` 均为当日,无一落入请求区间。
**处理**:核查方"HTTP 200 不构成参数生效证据"的提示正确,后续以 `openapi.json` 中参数是否存在作为发版判据。发版后重新验证。

### 5 · macro 模块无新条目

**结论**:成立,现已恢复。
**依据**:复核时 08-18 新增 86 条、08-19 新增 19 条,抓取已恢复;但 08-18 批次中 69 条含 `value` 的观测无一带 `unit`,仍为旧代码产出。
**处理**:观测期数与 `frequency` 字段同属未发版范围,发版后重新验证。

### 6 · 补图第二轮未覆盖新批次

**结论**:成立。
**依据**:全库 `image_probe` 共 4,200 条,均止于 08-15,之后无新增。新批次带图率 08-17 为 67.5%、08-18 为 68.1%、08-19 为 64.5%,全库 68.5%,由常规正文富化产生,与第二轮无关。
**处理**:发版后已确认运行,结论见第四节。

### 7 · 央行五源将导航元素作为日历事件入库

**结论**:成立。
**依据**:源 431 至 435 共 521 条,带 `event_date` 的为 0 条;标题实测为 `Upcoming`、`Speeches`、`Governors`、`Statistical releases` 等栏目名称。
**处理**:核查方指出"日期窗口在结构上无法拦截此类条目"的判断正确,其日期取自页面本身,恒为当日。本次已修改入库逻辑:calendar 模块条目缺少 `event_date` 一律不入库。
**限制**:要产出真实的央行日程,**数据源接口无法实现** —— 该五家官网未提供日历 API 或 ICS 订阅,通用爬虫无法判别页面元素是否构成一个事件,需逐源开发专用解析或改抓官方日程页面,另行排期。

### 8 · calendar_type 混入区域值

**结论**:部分成立。
**依据**:区域取值确实存在(全球 687 · 英国 / 日本 / 欧元区 各 100 · 美国 99 · 港交所信披 5 · 中国/港股 5 · 中国 2),声明的 13 个值中 7 个零命中,两项均属实。但"该 451 条仅为 08-15 单批遗留、非持续产出"一项不成立:源 416 的 `全球` 在 08-17、08-18、08-19 三个批次分别新增 206、255、186 条。
**处理**:源 416 的 L1 分类为 `3. IPO/上市`,新代码按 L1 取值后 `calendar_type` 为 `IPO`,区域移入 `calendar_region`。发版后重新验证。

### 9 · 源 416 脏条目与注册用途不符

**结论**:成立,实际情况较核查文档所述更为严重。
**依据**:全库 721 条中,带 `cik` 与 `form_type` 的真实申报仅 34 条且全部产生于 08-15;其余 687 条脏条目在 08-17 至 08-19 期间仍在每日新增。脏条目形态与核查文档一致(`333-297525`、`Natixis Commercial Mortgage Securities LLC (0001693143) (Filer)`)。
**处理**:发版后重新验证,新增的 `event_date` 入库门槛作为第二道拦截。
**待定夺**:注册表将该源登记为"锁定期解禁 (lock-up)",实际内容为 S-1 / 424B 发行申报,下游若按 lock-up 语义消费会出现偏差。需产品侧确认调整注册表登记还是更换抓取目标,本次未作变更。

### 10 · 源 437 默认页仍在库

**结论**:成立。
**依据**:`nginx.com` 与 `nginx.org` 两条仍可从 API 取到,`calendar_type` 为 `中国`,均属 08-15 批次遗留。此前答复中"脏数据已删"一项未在生产环境体现。
**处理**:入库侧的默认页识别加上 `event_date` 门槛构成双重拦截,发版后重新验证;两条历史数据随 7 天窗口自然过期。
**限制**:要取得真实招标日历,**数据源接口无法实现** —— 该站按来源 IP 限制访问,服务器出口地址仅能取到 nginx 默认页,需配置境内出口代理或更换数据源。

### 11 · news 脏时间戳

**结论**:成立。
**依据**:`published_at` 晚于 `fetched_at` 一小时以上的共 547 条,其中源 82 占 545 条,源 307 与 371 各 1 条。此前答复中列举的源 101 为举例失当,予以更正。相对采样时刻的未来时间戳确为 0 条。
**处理**:偏移量为平均 1.5 小时、最大 5.67 小时,均低于 6 小时的判脏阈值,因此按"绝对未来时间"判定的清洗规则不会命中,属阈值设置问题。本次已调整为按量级分级处理:阈值以内视为源端时钟或时区错误,取值钳制到抓取时刻;超出阈值仍置空。1.5 小时的偏差不足以支持丢弃整个日期。

### 12 · macro 缺 frequency 字段

**结论**:成立。
**依据**:macro 模块 payload 键实测仅有 `indicator`、`period`、`value`、`unit`,全库无 `frequency`。含 `value` 而无 `unit` 的观测已由核查时的 6 条扩大至 92 条,08-18 与 08-19 两个批次全部无 `unit`。
**处理**:`unit` 与 `frequency` 在取数侧为同一处逻辑写入,同属未发版范围,发版后重新验证。

### 13 · 源 448 / 422 停用后旧数据未清

**结论**:成立。
**依据**:两源最后一批数据均止于 08-15,之后无新增,停用已生效;源 465 在 08-17 至 08-19 稳定产出 30、37、35 条。历史条目源 448 剩 110 条、源 422 剩 4,275 条。
**处理**:两批历史数据随 7 天保留窗口自然过期,不另行清理。在此之前,核查方提出的"消费侧仍需按重复容错"建议成立。

### 14 · 五个 company 源本轮未抓

**结论**:现象成立,成因需要更正。
**依据**:这五个源在此期间持续被抓取,未产生新行的原因是去重 —— 抓取内容与 08-15 批次逐条相同,`external_id` 命中已有记录,因此 API 中不会出现新的 `fetched_at`。源 466 / 468 / 476 的 `skipped` 改造未部署,骨架条目仍在库(各 8、5、8 条)。
**处理**:发版后重新验证。
**限制**:源 466 / 468 / 476 要产出真实数据,**数据源接口无法实现** —— 三站均为纯客户端渲染,服务端 HTML 仅有骨架,且未提供公开接口。

## 八、本次复核新发现的问题

**各数据源的 `频率` 配置在生产环境未生效,全部数据源实际只在 4 小时一次的全量刷新中被抓取一次。**

依据:源 82 注册频率为 `10-15分钟`、源 531 为 `实时`,但两者的运行记录严格分布在 00、04、08、12、16 UTC;16:11 至 18:25 之间全站无任何抓取记录;300 份刷新报告的时间间隔均为 4 小时。

原因:`datahub/scheduler/service.py:101` 中,按频率注册的任务传入了 `next_run_time=None`。在 APScheduler 3.x 中该参数显式传 `None` 的语义是以暂停状态加入任务,因此 1,230 个按频率排程的任务从未触发;全局刷新、正文富化、保留期清理三个任务未传该参数,运行正常。

影响与处理:移除该参数即可修复,但这意味着 1,230 个数据源将立即按各自声明的节奏运行(`实时` 为 2 分钟一次)。该主机在正文富化任务运行期间已出现 API 响应劣化,因此需先确定节流方案。三个可选方向:维持现状的 4 小时全量刷新;仅放开 P1 优先级数据源的频率;全部放开并同步收紧并发。本次未作修改,待确认后执行。
